# sitecheck — 주소 하나로 네 가지 판정

지번 주소를 넣으면 위성 정사영상과 공공 대장에서 **건물 폴리곤 · 야적물 · 이격거리 ·
건축물대장 대조**를 뽑아 **하나의 JSON** 으로 냄. 네 결과 모두 같은 형식(GeoJSON
Feature)이고 판정도 같은 이름의 key 에 담기므로, 지도에 그대로 얹거나 한 번에 읽을 수 있음.

**진입점은 셋이고, 서로 무엇이 다른지가 이 세 줄이 전부임.**

| | 건물 폴리곤 | 사람 손 | 산출물 |
|---|---|---|---|
| `run.py` | 모델 추론 | **있음** (`hand_writting.TABLE_MODEL` — 데모 4주소) | `out/<주소>/result.json` |
| `demo.py` | GT(사람이 그린 정답) | **있음** (`hand_writting.TABLE` 을 읽는다) | `out_gt/<주소>/demo.json` · `out_gt/위성_비교분석_*` |
| `hand_writting.py` | GT | **있음** (주소별 손보정) | `demo/` 3건 · `demo_cmp/` 2건 — 저장소에 담긴 것 |

명령줄 · 단계 · 판정 · 저장물은 셋이 **완전히 같다** — [[sitecheck/analyze.py]] 한 길을 지나고
[[sitecheck/cli.py]] 한 벌의 깃발을 씀. **사람이 확인해 넣은 값은 `hand_writting.py` 한 곳에**
있고 셋이 다 그 표를 읽는다 — 모델 경로는 `TABLE_MODEL`, GT 경로는 `TABLE` 임. **표에 없는
주소는 손보정이 하나도 안 걸리므로** 그 수치는 전부 모델과 규칙이 낸 것이다(6절).

```bash
git lfs install && git clone <INTERNAL_REPO_URL>
cd building_segementation_model_inference
uv venv --python 3.10                             # 뿌리에 .venv/ — 하나면 된다(5절)
uv pip install -r requirements.txt                # 8 GB 쯤 · 캐시가 비면 2~10분
.venv/bin/python -m sitecheck.tools.check         # 무엇이 있고 무엇이 없는지 묶음별로
.venv/bin/python run.py "경상북도 구미시 공단동 293-15"
```

클론하면 **코드 · 가중치 1개(659 MB) · 건물 GT · 정사영상 3장 · GIS건물통합정보(4.8 GB)**
가 함께 온다(LFS 6.5 GB · 받은 뒤 디스크는 작업본까지 13 GB 쯤 쓴다). 손으로 넣어야 하는 것은
**API 키 하나**뿐이다(`assets/.env.geodata` · `.env.openai` · 형식은 `.env.*.example`) —
환경은 위 uv 두 줄이고, 모델·가중치·영상은 이미 안에 있음. `python -m sitecheck.tools.check`
가 무엇이 없는지 그대로 짚어 줌.

폴더는 **진입점과 코드를 나눠** 둠. 바깥에는 돌리는 것과 목록만 있음.


## 1. 처리 단계

| 단계 | 하는 일 | 입력 | 근거 항목 |
|---|---|---|---|
| **0 주소 해석** | 주소 → 좌표 → 필지(PNU) → 건축물대장 → 담당 정사영상 선택 | V-World · 공공데이터포털 | — |
| **1 건물 폴리곤** | 정사영상에서 지붕 외곽선 추출. 필지 주변만 잘라 추론 | 정사영상 + **단일 모델**(DINOv3 동결 + Mask2Former · 8대칭 TTA) | — |
| **2 야적물** | 「필지 − 건물」 구역을 타일로 잘라 VLM 판독 → 분류 · 이격 | 정사영상 + VLM | A4 · A5 |
| **3 이격거리** | 건물마다 **동서남북** 각 방향의 최단거리 → 측정선. 층수는 그 건물이 선 필지의 대장에서 | 1단계 결과 | A1 |
| **4 대장 대조** | 실측 건축면적 vs 대장 건축면적 | 1단계 결과 + 대장 | A3 |

단계는 순서가 있고, **앞이 실패해도 뒤를 건너뛰되 그 사실을 결과에 적는다**
(`provenance.steps` · 레이어별 `note`). 빈 결과를 그냥 내면 '건물 0동'과 '영상 없음'이
같은 모양이 되어 구분되지 않음.

### 2.1 최상위 key

| key | value 예시 | 뜻 |
|---|---|---|
| `schema_version` | `"1.3"` | 출력 형식 판. **1.1 = 좌표가 지도 프레임**(7절) · **1.2 = 건물 id 규약·`context`** · **1.3 = `owner` 가 PNU**(8절) |
| `crs` | `"EPSG:4326"` | **모든 좌표가 (경도, 위도)** |
| `frame` | 아래 7절 | 좌표가 어느 기준인가 — `"map"`(지도 좌표). 되돌린 양·근거도 여기 |
| `request` | `{ "address": "…", "requested_at": "…" }` | 무엇을 물었나 |
| `site` | 아래 2.2 | 어디인가 — 좌표 · 필지 · 대장 · 영상 |
| `layers` | 아래 2.3 | 무엇이 나왔나 — 네 레이어 모두 GeoJSON FeatureCollection |
| `summary` | 아래 2.4 | 레이어별 판정 수준 개수 + 최고 판정 |
| `provenance` | 아래 2.5 | 무엇으로 냈나 — 재현에 필요한 최소값 |

```jsonc
{
 "schema_version": "1.3",
 "crs": "EPSG:4326",
 "frame": { "name": "map", "crs": "EPSG:4326", "image_offset_m": [6.92, 5.11] },
 "request": {
  "address": "경상북도 구미시 공단동 293-25",   // 넣은 주소 그대로
  "requested_at": "2026-08-18T14:50:44+09:00"  // 조회 시각(로컬 타임존 포함)
 }
}
```

### 2.2 `site` — 어디인가

| key | value 예시 | 뜻 |
|---|---|---|
| `point` | `{ "lon": 128.3829377, "lat": 36.0939343, "addr_type": "PARCEL" }` | 지오코딩 결과. `addr_type` 은 `PARCEL`(지번) / `ROAD`(도로명) |
| `pnu` | `"4719011300102930025"` | 필지 고유번호 19자리 — 건축물대장 조회 key |
| `parcel` | `{ "type": "MultiPolygon", "coordinates": [ … ] }` | 연속지적도 필지 경계 |
| `parcel_m2` | `3770.4` | 필지 면적 |
| `scene` | `{ "key": "gumi", "ko": "구미", "res_m": 0.5, "size": [11900, 12612], "bbox": [ … ] }` | 쓴 정사영상. `res_m` 은 지상 해상도(m/px) |
| `ledger` | 아래 | 건축물대장 표제부 — **동별** 배열 |
| `neighbors` | `[ { "pnu": "…", "geometry": { … }, "ledger": [ … ] } ]` | 인접 필지와 그 대장 — 이격 판정의 층수 출처 |
| `notes` | `["영상 지오레퍼런스를 보정했다 — …"]` | 이 주소에서 특별히 한 일 |
| `georef` | `{ "offset_m": [6.92, 5.11], "origin_shift": [...], "px": [...], "steps": [...], "src": "국소(…) + 모델정합(…)" }` | **영상 쪽 보정.** `offset_m` 은 원본 영상이 실제보다 밀려 있던 양(m, 동·북)이고 이미 되돌렸음. `origin_shift` 는 지오트랜스폼 원점에 실제로 더한 값(장면 좌표계) |
| `parcel_bias_m` | `[-2.0, 25.0]` | **연속지적도 필지 레이어만** 옮긴 양(m, 동·북). 영상을 고쳐도 남는 어긋남이다 — 대구는 필지가 24 m 남쪽에 있었다 |
| `parcel_bias` | `{ "pairs": 46, "frac0": 0.616, "frac": 0.993 }` | 그 판단의 근거 — 자기 PNU 건물이 필지 안에 드는 비율의 보정 전/후 |
| `error` | `null` | 실패 사유. 값이 있으면 뒤 단계는 돌지 않았다 |

```jsonc
"ledger": [                                  // 건축물대장 표제부(getBrTitleInfo)
 { "dong":           "주2동",                 // 동 이름 (없으면 null)
   "main_purpose":   "공장",                  // 주용도
   "struct":         "일반철골구조",           // 구조 — 요율 산정의 1차 축
   "roof":           "기타지붕",               // 지붕재
   "arch_area_m2":   790.1,                  // 건축면적 ← 위성 실측과 대는 값
   "total_area_m2":  786.0,                  // 연면적 (층수가 곱해져 비교 대상 아님)
   "floors_above":   1.0,                    // 지상 층수 ← A1 이격 기준(6 m / 10 m)을 가른다
   "floors_below":   0.0,
   "use_approval":   "20200311",              // 사용승인일
   "pnu":            "4719011300102930025" }
]
```

### 2.3 `layers` — 무엇이 나왔나

네 레이어 모두 GeoJSON **FeatureCollection** 이고, 껍데기 key 가 같음.

| key | value 예시 | 뜻 |
|---|---|---|
| `type` | `"FeatureCollection"` | GeoJSON 표준 |
| `layer` | `"separation"` | 레이어 이름 |
| `count` | `2` | Feature 개수 |
| `features` | `[ … ]` | 아래 |
| `note` | `"OPENAI_API_KEY 없음 — 판독 모델을 부를 수 없다"` | **못 낸 이유**(제대로 냈으면 없다). `count: 0` 이 '없다'인지 '못 쟀다'인지 여기서 갈린다 |

**판정 4종은 네 레이어가 모두 같은 key 에 담음.** 레이어가 늘어도 소비자 코드는 그대롬.

| key | value 예시 | 뜻 |
|---|---|---|
| `level` | `"경고"` | 경고 / 해당 / 주의 / 참고 / 기록 / 이상없음 / 정보없음 — **표시 문구의 정본** |
| `level_rank` | `0` | 위 목록 안의 자리(0 이 가장 먼저 볼 것). **정렬·비교용**이고 등급 이름이 아니다 — 받는 쪽이 한글 문자열 7개를 다시 늘어놓지 않아도 「나쁜 것부터」가 된다 |
| `label` | `"연소확대 우려"` | 한 줄 판정 |
| `reason` | `"한쪽이라도 2층 이상 · 실측 3.9 m — 법정선 10 m 미달"` | 왜 그 판정인지 — **실측값과 기준값이 같이** 들어간다 |
| `basis` | `"소방시설법 시행규칙 제17조 제2호"` | 근거 조문 |

`level` 값의 뜻

| level | 뜻 |
|---|---|
| `경고` · `해당` | 법정선 미달 — 현장 확인 대상 |
| `주의` | 법정선 + 측정오차 이내 — 판정이 오차에 걸린다 |
| `참고` | 법정선은 충족하나 협회 권장선 아래 |
| `기록` · `이상없음` | 기준선 충족 |
| `정보없음` | **재지 못했다** (없다는 뜻이 아니다) |

#### `buildings` — 건물 지붕 외곽선 (Polygon)

판정을 붙이지 않는 **관측값** 레이어다(`level` 등은 `null`). 나머지 셋이 이 위에 섬.

```jsonc
{ "type": "Feature", "id": "B0001",
  "geometry": { "type": "Polygon", "coordinates": [ /* 지붕 외곽선 */ ] },
  "properties": {
    "bld_id":         "B0001",   // 건물 번호 — 8절
    "role":           "subject", // 이 지번 건물
    "dong":           "A동",     // 사람이 읽는 이름 — 건축면적 큰 순(설계서 BR-13)
    "score":          0.972,     // 모델 신뢰도 (settings.SCORE_THRESHOLD 이상만 남는다)
    "arch_area_m2":   812.0,     // 실측 건축면적 — 지붕 수평투영면적(EPSG:5179 투영)
    "source":         "model",
    "merged_from":    1,         // 합친 조각 수. 모델이 큰 공장동을 쪼개 내면 2 이상
    "in_parcel_frac": 1.0,       // 이 필지에 걸친 면적 비율. 0.5 미만은 옆 필지 건물로 뺀다
    "owner":          "4719011300101500000",  // **이 건물이 선 지번(PNU)** — site.neighbors 로 푼다
    "owner_by":       "footprint", // 어떻게 정했나: footprint(GIS 가 말했다) / parcel(필지 지분)
    "registered":     true,        // = owner_by == "footprint". ledger 레이어의 같은 이름과 뜻이 다르다
    "level": null, "label": null, "reason": null, "basis": null } }
```

#### `ledger` — 대장 대조 A3 (Polygon)

```jsonc
{ "type": "Feature", "id": "A3:PARCEL:4719011300102930025",
  "geometry": { "type": "MultiPolygon", "coordinates": [ /* 필지 */ ] },
  "properties": {
    "level":  "이상없음",
    "label":  "증축으로 보지 않음",
    "reason": "대장 합계 1,659 ㎡(2동) · 실측 합계 1,647 ㎡(2동) · 초과 -12 ㎡(-1 %)",
    "basis":  "건축법 제14조 제1항 제1호",
    "scope":           "parcel",   // "parcel" = 필지 총량(정본) · "building" = 동별
    "pnu":             "4719011300102930025",
    "measured_sum_m2": 1647.1,     // 모델이 잰 건축면적 합
    "ledger_sum_m2":   1658.6,     // 대장 건축면적 합
    "n_model":         2,          // 모델 건물 수
    "n_ledger":        2,          // 대장 동 수
    "authoritative":   true,       // 정본 판정인가
    "detection_ratio": 0.993 } }   // 실측/대장 — 1 에 가까울수록 모델이 다 잡았다
```

`scope: "building"` 인 동별 판정에는 `bld_id` `measured_m2` `ledger_m2` `ledger_dong`
`ledger_struct` `registered`(등록 footprint 유무) `attached`(등록 건물에 붙었나)가 더 붙음.
**동별 판정은 등록 footprint(GIS건물통합정보)가 대장 건축면적을 90 % 이상 설명할
때만 냄.** (보고서는 그 판정이 없을 때 **면적으로 맞춘 추정 대응**을 따로 세워 표를 채운다 —
`report/single._pair_by_area`. 한 대장 동에 판독 동 여럿을 묶으므로 「조각 수만큼 미등록」이
되지 않고, 동별 차이의 합이 총량 차이와 정확히 맞음. 추정임은 표 제목에 적음.) 못 하면 동별 대응을 하지 않고 필지 총량 판정만 낸다 — 대장에는 위치가 없어
어느 건물이 어느 동인지 footprint 없이는 알 수 없기 때문임.

#### `separation` — 이격거리 A1 (LineString)

**조문이 둘이라 세는 규칙도 둘임.** 거리는 양쪽 모두 두 지붕 외곽선 사이의 최단거림
(축에 투영한 값이 아니다 — 투영하면 비스듬히 마주 선 건물이 실제보다 멀게 나와 연소 우려를
과소평가한다). 세는 규칙과 그 근거값은 `rules.py` 의 「무엇을 한 쌍으로 세나」 한 곳에 있음.

**필지 안** — 제17조 제2호가 직접 말하는 구조(대지경계선 안 둘 이상 건축물)라 **쌍마다 한
줄**임. 걸을 경계선이 없으므로 구간이라는 것이 없음. 탐색반경(`SEARCH_M` = 60 m)까지 재고
**도달거리로 자르지 않는다** — 자르면 18 m 떨어진 두 동이 선 필지에서 표가 「이 지번 건물이
하나뿐」이라고 말한다(실측 고잔동 672-6 A동↔B동 18.03 m). 쌍은 양쪽에서 한 번씩 두 줄로
나오고(`pair[0]` 이 늘 이 지번 건물), 보고서 표는 한 쌍을 한 줄로 접음.

**필지 밖** — 조문 밖이지만 연소는 경계를 넘음. **대지경계선을 북쪽부터 시계방향으로 걸으며
자리마다 가장 가까운 상대 하나**를 고른다(걸음 `SEP_WALK_STEP_M` = 2 m). 임자가 바뀌는 곳이
구간 경계이고, 구간들은 경계선의 분할이라 빈틈도 겹침도 없다 — 「부지를 한 바퀴 돈다」가 정렬
규칙이 아니라 **구조**가 됨. 여기도 도달거리로 자르지 않는다(18 m 떨어진 쪽은 「이상없음
18 m」로 적고, 줄이 없는 것은 「그쪽 60 m 안에 아무것도 없다」는 뜻으로만 쓴다).

한 구간에 **도달거리(11.3 m) 안으로 마주 선 우리 동은 전부** 한 줄씩 낸다 — 하나만 고르면 두
번째 경고가 조용히 사라진다(실측 호림동 3-10 의 남쪽 구간: B동 1.9 m 옆에 A동 3.2 m 가 있고
둘 다 법정선 미달인데 A동 줄이 없었다). 도달거리 안에 아무 동도 없으면 가장 가까운 동 하나로
그 구간을 대표한다 — 구간은 경계선의 분할이라 빈 구간을 둘 수 없음. `front_m`(마주한 폭)은 그
**상대가** 마주하는 경계선 길이라 같은 구간의 두 줄에 같은 값이 붙음.

옛 규칙(「건물마다 둘레 25 m 안의 상대 전부」)은 폐기했다 — 안쪽에 갇힌 동까지 바깥 건물맘
선이 이어져 부지를 가로지르는 선이 깔렸고, 줄 수가 물건당 9.6줄이었다(경계선 걷기는 6.2줄).
`ADJACENT_M` 이라는 이름은 `rules.py` 에 이제 없음.

**구간을 아예 못 이긴 상대는 손으로 더할 수 있다**(`s3_separation.run(also=)` · 데모는
`hand_writting.py` 의 `sep_also`). 자리마다 최근접 하나만 세므로 두 상대에게 끼인 건물은 어느 자리도
못 이겨 표에서 빠진다 — 실측 호림동 3-10 의 남서쪽 건물은 우리 동에서 4.9 m 인데 남쪽·서쪽
건물이 모든 자리를 이겨 줄이 없었음. 그런 줄은 `hand: true` 를 달고 **`front_m` 을 비운다**
(마주한 폭이 0 인 것이 아니라 「어느 자리도 이기지 않았다」가 맞는 말이다). 거리·방위·판정은
이긴 줄과 같은 코드로 냄.

**GT 지붕선이 그늘까지 물린 자리는 사람이 옮긴다**(`settings.NEIGHBOR_SHIFT`). GT 는 사람이
그린 것이라 지붕 경계에 그늘·차양이 물려 들어오기도 하고, 그 폴리곤으로 이격을 재면 **바닥을
지붕으로 세어** 두 건물이 붙은 것처럼 나온다 — 호산동 702-5 의 ③(N0016)은 폴리곤 윗변이 우리
A동에서 0.25 m 였는데 원본 픽셀의 밝기를 세로로 훑으면 지붕이 시작하는 자리는 2.65 m 남쪽임.
값은 `(bld_id, PNU, (동,북) m)` 이고 **지번이 맞을 때만** 옮긴다(`NEIGHBOR_DROP` 과 같은 규약).
적용은 `s1_building.label_features` 한 곳이며 **id 를 붙인 뒤**라 번호가 밀리지 않고, 방향·거리를
재기 전이라 이격·그림·표가 옮긴 자리에서 다시 나옴. 면적은 평행이동이라 그대로고, 옮긴 사실은
`site.notes` · 건물 레이어 note · 그 Feature 의 `shift_m` 에 남음.

결과는 **둘레 위 자리(`arc_m`) 순**으로 늘어놓는다 — 표를 위에서 아래로 읽으면 부지를 한
바퀴 도는 순서가 되고, 지도의 ①②③(`draw.ext_names`)도 같은 자리에서 번호를 받으므로 표의
외부건물 번호 칸과 지도의 배지가 1:1 로 맞음. 보고서는 그 순서로 **대상 동마다 한 표**를
싣는다(「A동 이격거리 측정 결과」·「B동 …」) — 열은 **이격 번호 · 외부건물 번호 · 방위 ·
이격거리 · 판정** 다섯이고(2026-08-27), 필지 안 상대는 외부건물 번호 칸에 **상대 동 이름**이
옴. 방위는 보는 쪽에 따라 뒤집히므로(A 의 남 = B 의 북) 필지 안 쌍은
접지 않고 두 표에 한 줄씩 섬.

**보고서·그림은 여기서 하나를 뺀다**(`draw.sep_pairs`) — **우리 동끼리 눈금(0.5 m) 이하로 붙은
쌍**이다(아래). 옆 지번 건물은 눈금 이하라도 빼지 않음. 잰 값은 `separation` 레이어에 그대로
남음.

`dir`(4방위)은 `--skip-dir` 로 도로면을 뺄 때만 쓰고, 사람이 읽는 방위는 `dir8`(8방위)임.

**영상 1 px(0.5 m, `rules.SEP_TOUCH_M`) 이하면 잰 값을 적지 않고 「0.5 m 이하」로 적는다**
(등호를 포함한다 — 눈금 그 자체와 그 아래는 가릴 수 없다). 지붕 폴리곤이 붙어 있다는 뜻일
뿐, 실제 외벽 사이가 붙었는지 좁은 통로인지는 이 영상으로 가릴 수 없다 — 704-1 의 B동↔C동은
0.06 m 로 나오지만 원본 픽셀을 8배로 확대하면 그 자리에 3~4 px(약 1.5~2 m) 폭의 어두운 띠가
있다(사람이 지붕 두 장을 골짜기 가운데선까지 그렸다). **우리 동끼리**는 떨어진 거리가 아니라
한 덩어리라 보고서·그림의 표에서 뺀다 — 그래서 동별 표에 필지 안 줄이 없을 수 있음. 표가
아예 빌 때는 「둘레에 마주 선 건물이 없음 · 해당 없음」이라 적어 **잴 상대가 없는 것**과 못 잰
것을 가림. 옆 지번 건물은 빼지 않는다(`draw._own_touch`) — 「맞닿음」이라는 말은 쓰지 않음.
붙었다는 것은 이 영상으로 확정할 수 없는데 그 말은 확정한 것처럼 읽힘.

최근접점을 잇는 **선 그 자체가 잰 거리다**. 길이 = `dist_m` 이라 도형과 숫자가 어긋날 수 없음.

```jsonc
{ "type": "Feature", "id": "S:B0020:B0000",
  "geometry": { "type": "LineString", "coordinates": [ /* 최근접 두 점 */ ] },
  "properties": {
    "level":  "경고",
    "label":  "연소확대 우려",
    "reason": "한쪽이라도 2층 이상 · 실측 3.95 m — 법정선 10 m 미달",
    "basis":  "소방시설법 시행규칙 제17조 제2호",
    "pair":        ["B0020", "B0000"],  // 잰 두 건물 — 앞이 이 지번의 건물
    "dir":         "동",                // 4방위 — `--skip-dir` 가 도로면을 뺄 때 쓴다
    "dir8":        "북동",              // 8방위 — 표·지도에 적는 방위
    "az_deg":      41.3,                // 방위각(북=0, 시계방향) — 도는 순서를 정한다
    "dist_m":      3.95,                // 외벽 간 거리(m) — EPSG:5179 투영해서 잰다
    "floors":      [1, 2],              // 각 건물 지상 층수 — 6 m / 10 m 기준을 가른다
    "floors_src":  ["ledger", "empty"],    // 그 층수를 어디서 얻었나 — 아래
                                        //   ledger        그 건물이 선 필지의 대장 (확실)
                                        //   empty         필지는 찾았으나 대장에 층수가 없다
                                        //   nearest       필지를 못 찾아 **가장 가까운** 필지의 대장 (추측)
                                        //   nearest_empty 위와 같은데 그 대장에도 층수가 없다
                                        //   none          필지 색인 자체가 없다
    "same_parcel": false,               // 같은 필지 안의 두 동인가 — 안·밖을 따로 낸다
    "run_id":      2,                   // 필지 밖만 — 구간 번호(북부터 시계방향, 1부터)
    "front_m":     50.3,                // 필지 밖만 — 그 상대가 마주하는 대지경계선 길이
                                        //   같은 구간의 두 줄에 같은 값 · `hand` 줄은 null
    "front_d_m":   0.0,                 // 필지 밖만 — 구간 중앙에서 그 상대까지(임자를 가른 거리)
    "arc_m":       58.3,                // 필지 밖만 — 구간 중앙의 둘레 위 자리(m) · 정렬·번호의 정본
    "hand":        true,                // 손으로 더한 줄일 때만 — 구간을 못 이긴 상대(`also=`)
    "caveat":      "개구부 방향·내화구조 여부는 위성에서 확정할 수 없다 — 현장 확인 대상" } }
```

#### `yard` — 야외 적재물 A4·A5 (Polygon)

```jsonc

  "geometry": { "type": "Polygon", "coordinates": [ /* 적재 구역 */ ] },
  "properties": {

    "cls":     "timber_pallet",        // A4 분류 4종 중 하나 (3절)
```

### 2.4 `summary` — 한눈에

```jsonc
"summary": {

```

### 2.5 `provenance` — 무엇으로 냈나

없으면 나중에 수치를 설명할 수 없음. 모델을 바꾸거나 규칙을 고치면 여기 값이 달라짐.

```jsonc

   "yard_vlm":        "gpt-5.6-terra",   // 야적 판독 모델 (--no-yard 면 null)

   "score_threshold": 0.10 },            // 운용 임계값 — 이 아래 폴리곤은 버린다

            { "step": "buildings", "ok": true,  "note": "2동 (옆 필지 36동)" },
            { "step": "yard",      "ok": false, "note": "건너뜀" } ],
```

## 3. 판정 기준

전부 `rules.py` 한 곳에 있음. 값이 흩어지면 리포트마다 다른 숫자가 나오고, 그때 어느 쪽이
맞는지 사후에 알 수 없음. 출처는 근거문서 `PoC_결정항목_기준근거_A1_A3_A4_A5` (2026-08-13).

| 항목 | 기준 | 근거 |
|---|---|---|
| **A1** 이격거리 | 외벽 간 1층 **6 m** · 2층 이상 **10 m** 미만 → 경고<br>+ 측정오차 1.3 m 이내면 → 주의 | 소방시설법 시행규칙 제17조 |
| **A3** 대장 대조 | 초과 30 ㎡ 미만 또는 10 % 이하 → 증축으로 보지 않음<br>30 ~ 85 ㎡ → 증축<br>85 ㎡ 이상 → 증축 · 현장 확인 대상 | 건축법 제14조 제1항 제1호 |
| **A4** 야적 분류 | `timber_pallet` 목재·팔레트 / `plastic_rubber` 합성수지·고무 /<br>`waste_recycle` 폐기물·재활용 / `other_stock` 그 밖<br>고철·토사·차량은 **이름을 주고 버린다** | 화재예방법 시행령 별표2 |
| **A5** 야적 이격 | 건물까지 **6 m** 미만 → 해당<br>6 ~ 15 m → 참고(KFS-0760) | 별표3 다목 · KFS-0760 |

**「위반」이라고 쓰지 않음.** 근거 조문이 저장·구조 요구 규정이지 이격을 금지하는 규정이
아님. 문구는 「해당 · 현장 확인 필요」다.

**야적에서 수량과 면적은 내지 않음.** 별표2 수량은 kg·㎥ 라 위성으로 못 재고, 별표3
나목의 50 ㎡ 는 '쌓는 부분' 1개 기준인데 검출 단위는 구역 전체라 단위가 다름.

| `sitecheck/rules.py` | A1·A3·A4·A5 판정 규칙과 임계값의 **단일 출처**. 법령 근거 문구도 여기 |

### 머리글 형식 — 샘플의 **신판**을 따름

판짜기를 재 온 「지반침하 위험 보고서 샘플」은 두 판이 있고, **둘의 상단이 다르다**(실측
2026-08-25).

| | 구판 `지반침하_보고서샘플.pdf` | 신판 `…_주의_누적구역.pdf` ← 지금 따르는 것 |
|---|---|---|
| 로고 | 구(舊) 로고 (728×135) · 높이 14.2 pt | **고객사 워드마크만** (435×124) · 높이 17.6 pt |
| 선 | **도련까지 닿는 전폭 띠** · 두께 3.4 pt · 남색 | **로고 폭만큼의 밑줄** · 두께 1.2 pt · 밝은 파랑 `#003cdc` |
| 제목 | 15 pt · `#1a1a1a` · 왼 여백 41.7 pt | 12 pt · `#111827` · 왼 여백 39.7 pt |
| 절 글머리 | ■ 가 **글자와 같은 먹색** | **■ 만 밑줄과 같은 파랑** · 글자는 진회색 |

우리 보고서는 원래 **구판**을 그대로 옮겨 놓은 것이었다(여백 14.7 mm · 제목 15 pt · 전폭
남색 띠가 그 흔적이다). 2026-08-25 에 **상단과 절 글머리**를 신판으로 바꿨다 — 로고 ·
밑줄 · ■ 색 셋임.

■ 는 **한 줄을 두 번 그려** 앞 글자만 덮는다(PDF). 「■ 」 의 폭을 재서 글자를 밀어 놓는
길도 있지만 그 폭은 글꼴·크기마다 달라, 숫자로 적어 두면 글꼴을 바꿀 때 조용히 어긋난다 —
같은 자리에 겹쳐 그리면 글리프 윤곽이 정확히 포개지므로 잴 것이 없음. HTML 은 `h2::before`
에 색만 줌. 손판 PDF 는 ■ 가 제 몫의 span 이라 그 자리만 지우고 다시 앉힘
([[sitecheck/report/refit.py]] `blue_bullets`).

**제목 크기·여백은 안 바꿨음.** 그 둘은 본문 전체의 세로 흐름을 정하는 값이라, 바꾸면
`demo/`·`demo_cmp/` 의 **손으로 만든 PDF 5부를 다시 짜야 한다**(그 판은 코드가 못 뽑는다 —
6절). 화면(HTML)만 바꾸면 같은 물건의 종이와 화면이 갈림.

밑줄의 **폭은 코드에 숫자로 없다** — 로고 그림의 가로세로비가 정함. HTML 은 로고를 감싼
`inline-block` 의 아래 테두리로, PDF 는 로고 축 상자의 폭으로 긋음. 로고를 바꾸면 밑줄이
저절로 따라옴.

## 5. 실행 환경 — 목록도 환경도 하남

```bash
uv venv --python 3.10                             # 뿌리에 .venv/
uv pip install -r requirements.txt                # 8 GB 쯤 · 캐시가 비면 2~10분
.venv/bin/python -m sitecheck.tools.check         # 다 초록이면 끝
```

이미 다른 곳에 같은 환경이 있으면 만들지 말고 경로만 준다:
`SITECHECK_PYTHON=/경로/bin/python`(모델만 다른 데서 돌리려면 `SITECHECK_DINOV3_PYTHON`).

**2026-08-27 에 둘을 하나로 합쳤음.** 어제까지는 파이프라인 `.venv`(torch 2.0 + `mmcv` 2.0)와
건물 모델 `.venv-dinov3`(torch 2.13 + transformers 5.15) 둘이었고, **「합칠 수 없다」가 그때는
맞았다** — `mmcv` 는 torch 버전에 맞춰 컴파일되는 패키지라 torch 를 올리면 그 자리에서 깨짐.

그 `mmcv` 를 **SAMPolyBuild 와 함께 걷어 냈다**(e22b9d8). 그러고 나니 파이프라인 쪽에 torch 를
쓰는 코드가 **한 줄도 없다** — `import torch`·`mmcv`·`lightning`·`pycocotools` 가
`sitecheck/vendor/dinov3seg/` 밖에서 하나도 안 나온다(실측). 막고 있던 것이 사라진 것이지
무리해서 합친 것이 아님.

**같은 값이 나오는 것을 확인하고 합쳤음.** 합친 환경으로 공단동 293-15 를 추론부터 다시
돌려(`--no-reuse`) 저장된 `out/` 결과와 대조했더니 건물 면적 · 이격 11줄 · 대장 판정 · 정합
잔차가 **한 자리도 다르지 않음.** 고정 패키지는 122 → 79개로 줄었음.

**모델은 여전히 서브프로세스로 돈다**(`settings.DINOV3_PYTHON`). 값이 없으면
`SITECHECK_PYTHON` 으로 떨어지므로 이 환경 하나로 돌고, 모델만 다른 환경에서 돌려야 할 날이
오면 그 깃발만 주면 된다 — 구조는 그대로 두고 인터프리터만 하나로 모은 것임.

**CUDA 버전은 이 장비에 맞춤.** 학습은 cu130 이었는데 그 휠은 드라이버 13.x 를 요구하고
이 장비는 535(CUDA 12.2)라 `torch.cuda.is_available()` 이 False 가 된다(실측 2026-08-26).
그래서 **torch 버전은 그대로 2.13.0** 이고 CUDA 런타임만 cu126 으로 맞췄다 — 12.x 안에서는
마이너 호환이 보장됨. 드라이버가 13.x 인 장비에서는 `--index-url .../cu130` 으로 바꾸면 됨.
`tools.check` 가 **그 파이썬에서 직접** torch·transformers·CUDA 를 불러 보고 찍는다 — 본체
환경의 torch 를 보고 초록불을 내지 않음.

예전에는 목록이 셋이었다(파이프라인용 · 추론용 · 그 lock). 나누면 무엇이 어느 환경에 속하는지
사람이 기억해야 하고, 두 환경의 `numpy`·`shapely` 가 조용히 갈린다 — 같은 폴리곤을 놓고
면적이 다르게 나오면 그 원인을 찾는 데 시간이 듦. torch 가 든 환경에 `geopandas`·`rasterio`
를 더해도 충돌이 없음을 실측으로 확인해 **하나로 합쳤다**(2026-08-19 · torch 2.0.0+cu117 ·
CUDA 됨 · geopandas 1.1.4 · rasterio 1.4.4). 모델은 그래도 서브프로세스로 돌린다 — GPU 메모리와
mmengine 전역 설정을 본체와 섞지 않으려는 것이고, 인터프리터는 같은 것을 씀.

**두 번 나눠 깔면 실패함.** CUDA 휠은 `download.pytorch.org`, 미리 빌드된 `mmcv` 는
openmmlab 인덱스에만 있어서, 인덱스를 명령 밖에 두면 mmcv 가 소스 빌드로 들어가 죽음.
그래서 인덱스를 `requirements.txt` 안에 적어 `uv pip install -r` 한 번으로 끝낸다(인덱스가
둘이라 `uv.toml` 의 index-strategy 도 함께 필요하다 — 이유는 그 파일 주석에).

**버전은 전이 의존성까지 다 고정**돼 있음. 이 환경은 버전에 예민한 것이 많아 풀어 두면 어제
되던 설치가 오늘 깨짐. 실측으로 걸렸던 것들이 그대로 목록에 주석으로 붙어 있다 —
`setuptools<70`(lightning 이 `pkg_resources` 를 쓴다) · `lightning-cloud==0.5.32` ·
`websockets<12`(핀을 빼면 `import lightning` 이 죽는다) · `pycocotools`·`prettytable`·
`scikit-image`(벤더한 코드가 쓴다) · `shapely` 는 2.0.7(2.0.1 은 정상 결과에도 numpy 경고를
뿜는다). 목록을 다시 만드는 방법도 파일 머리에 있음.

**모델은 하나고 ckpt 도 하나다** — DINOv3 ViT-L/16 을 **동결**한 채 Mask2Former 머리를
우리 데이터로 학습한 `models/building/dinov3_v2_run4_best_ep11.pth`(1.32 GB · LFS) + 8대칭 TTA.
원본은 `building_seg/dinov3_v2` 의 run4 이고, 코드는 `sitecheck/vendor/dinov3seg/` 에 그대로
담았다(무엇을 담고 무엇을 뺐는지는 그 폴더의 `ORIGIN.md`).

**창 512 px · 모델 입력 1024 px** 다. 학습이 512 crop 을 1024 로 올려서 봤으므로 그 배율을
지킨다 — 원본은 깃발 하나(`--tile-size`)로 두 값을 함께 정하는데, run4 산출물은 512 타일을
미리 잘라 두고 그 깃발을 체크포인트 `cfg` 의 1024 로 둔 상태에서 나왔음. 우리는 두 값을
따로 준다(`settings.INFER_DINOV3`). 이 이식이 원본과 같은 것을 내는지는 run4 가 낸
`output/run4/namdong` 을 다시 만들어 견줘 확인했다 — **폴리곤 IoU 중앙 0.984 · 면적합 비
1.004**(12타일 · 원본 436동 · 재현 433동). 그 표와 `--threshold 0.1` · `--tta` 를 어떻게
알아냈는지는 `vendor/dinov3seg/sitecheck_worker.py` 머리글에 있음.

운용 임계값은 **0.10**. **점수의 뜻이 바뀌었다** — 새 점수는 `cls × pred_iou` 로 **예측
IoU** 이고(잘 잡은 것 0.8 · 어중간한 것 0.4), 예전 모델의 포화된 신뢰도(0.85 근처)와 스케일이
다름. 예전 값 0.70 을 그대로 두면 잡힌 GT 의 43 %만 남고 300 ㎡ 미만은 한 동도 남지
않는다(실측). 표본 7창에서 크기별로 재서 고른 값이고, **이 지번 건물은 0.5 까지 임계값에
둔감하다**(11동 전부 · 헛것 없음) — 임계값이 실제로 가르는 것은 옆 지번 건물이고 그것을
놓치면 이격이 과소평가됨. 측정표는 `settings.SCORE_THRESHOLD` 주석에.

그 전 모델(SAMPolyBuild 파인튜닝 · `best.ckpt` · 659 MB)의 코드·가중치·임계값 근거는 그대로
남아 있다(`settings._SAMPOLY`). 되살리려면 그 줄을 `BUILDING_MODELS` 로 쓰고 `.venv` 로
돌리면 됨. **둘을 한 번에 돌리지는 마세요** — 점수 스케일이 달라 합의 재점수가 뜻을
잃는다(그 이유는 `settings.py` 주석).

`python -m sitecheck.tools.check` 가 무엇이 어느 쓰임에 필요한지 묶음별로 보여 줌.

## 6. 진입점 셋 — 무엇이 다르고 무엇이 같은가

| | 건물 폴리곤 | 사람 손 | 기본 산출 위치 |
|---|---|---|---|
| `run.py` | 모델 추론 (`s1_building.predict`) | **있음** (`hand_writting.TABLE_MODEL`) | `out/<주소>/result.json` · `out_cmp/위성_비교분석_*` |
| `demo.py` | GT (`gt.polygons`) | **있음** (`hand_writting.TABLE`) | `out_gt/<주소>/demo.json` |
| `hand_writting.py` | GT | **있음** | `demo/` 3건 · `demo_cmp/` 2건 |

**산출물이 두 종류이면 폴더도 둘이다** — 위험분석은 주소마다 폴더 하나인데 비교분석은 주소맘
보고서 한 부에 날짜분 폴더 둘(`t1/`·`t2/`)이 딸림. 섞으면 폴더만 보고 무엇이 무엇인지 알 수
없어서, 손보정 길이 `demo/`·`demo_cmp/` 로 갈라 둔 그 모양을 세 진입점이 다 따름
(`out/`·`out_cmp/` · `out_gt/`·`out_gt_cmp/`).

**모델 경로로 비교분석을 낼 때 알아야 할 것.** 2026-08-26 까지 `--compare` 는 GT 경로에만
열려 있었음. 이유는 방법론이다 — 비교는 「같은 지붕을 두 날짜에 놓고 보는 것」이라 GT 는 같은
폴리곤을 옮겨 쓰지만 모델은 날짜마다 새로 뽑음. 그 차이가 실측으로 이렇게 나온다(두 표본):

    호산동 A동 면적   모델 1,275 → 1,205 ㎡ (Δ−70 · −5.5%)  ·  GT 1,322 → 1,322 (Δ0)
    호산동 옆 지번    모델 29 → 27동                        ·  GT 31 → 31동
    신당동 옆 지번    모델 35 → 38동                        ·  GT 41 → 42동

`rules` 의 측정오차 문턱(이격 1.3 m · 면적 30 ㎡ 이면서 2 %)이 작은 흔들림은 「변화 없음」으로
떨어뜨리지만, **그보다 큰 경계 차이와 옆 건물의 등장·소멸은 통과한다** — 호산동 보고서에
「철거 또는 판독 누락」 1건과 이격 「변화 확인」 5건이 그렇게 들어갔다(신당동 9건). 종이가
거짓말을 하는 것은 아니다(문구가 「철거 **또는 판독 누락**」이고 둘 다 현장 확인 대상이다).
그래도 **모델 경로 비교분석은 변화 목록을 그대로 믿을 문서가 아니라, `t1`·`t2` 의
`0_모델건물.png` 두 장과 함께 보는 문섬.** 문턱을 모델 편차에 맞게 다시 재려면 두 촬영일
표본이 더 필요함.

```bash
python run.py            "경상북도 구미시 공단동 282"
python run.py --file cmp_addresses.txt --compare daegu daegu2   # → out_cmp/ (2건)
python demo.py           "경상북도 구미시 공단동 282"
python hand_writting.py                      # 저장소에 담긴 산출물 5건을 다시 낸다
python hand_writting.py --only demo|cmp|refit
python hand_writting.py --verify             # 손판 PDF 가 지금 값과 맞나
```

### 왜 GT 로도 내는가

판정이 **어떤 근거로 나오는지** 보여야 할 때 건물 폴리곤이 흔들리면 설명하려는 것이 가려짐.
모델 성능은 따로 재고(seglab 벤치), 여기서는 이격·야적·미등록 판정의 절차와 숫자만 보이게
함. GT 는 장면 전체에 있으므로(대구 2,651 · 구미 6,443 · 남동공단 4,748동) 주소는 영상
안이면 아무 곳이나 됨.

### 갈리는 것은 딱 둘

몸통은 [[sitecheck/analyze.py]] 하나이고, 세 진입점은 그 함수에 **두 값만 다르게** 줌.

    source   "model" | "gt"     건물 폴리곤을 어디서 얻는가
    hand     Hand                사람이 확인해 넣는 값 (기본은 빈 값)

명령줄도 한 벌이다([[sitecheck/cli.py]]) — 옵션 이름·기본값이 갈리면 「같은 조건으로 돌렸다」를
말할 수 없음. 산출물 형식도 같다(`result.json` / `demo.json`, 2절 그대로) — 다른 점은
`provenance.model.building` 이 모델 목록이냐 GT 파일 경로냐 하나뿐이고, 그림·문서를 만드는
도구는 두 파일을 구분하지 않고 같이 읽음.

### 손보정 — 열 가지, 한 곳

예전에는 손보정이 `settings.py`(넷)와 `tools/for_demo.py`(다섯)와 `draw.py`(하나)에 흩어져
있었고, **`run.py` 가 그중 다섯을 자기도 모르게 쓰고 있었음.** 그러면 「모델이 스스로 낸 값」
이라고 말할 수 없다 — 어느 수치가 사람 손을 탄 것인지 사후에 가릴 방법이 없기 때문임.

지금은 전부 `hand_writting.py` 의 `TABLE` 한 곳에 있다(열한 가지).

| 항목 | 무엇 |
|---|---|
| `parcel_fix` | 대지 경계를 자동 보정 위에 더 옮긴다 (동, 북) m |
| `ledger_fix` | 대장 **건축면적만** 갈아 넣는다 (연면적·층수·구조는 그대로 — 요율축이다) |
| `ledger_drop` | 대장에서 동을 뺀다 — 위성이 「없다」를 확정한 것이 아니라 사람이 정한 것 |
| `ledger_rename` | 대장 **동 이름**을 판독 동 이름에 맞춘다 — 둘 다 A·B·C 를 쓰면서 가리키는 건물이 엇갈릴 때만(신당동: 판독 A동↔대장 C동). 짝짓기는 이름이 아니라 면적으로 하므로 적히는 글자만 바뀐다 |
| `neighbor_add` | GT 에 없는 옆 지번 건물을 경위도 링으로 그려 넣는다 |
| `neighbor_drop` | 옆 지번 목록에서 아예 뺀다 (지도에도 안 그린다) |
| `neighbor_shift` | 그늘까지 물려 그려진 지붕 폴리곤을 옮긴다 |
| `sep_also` | 경계선 걷기에서 구간을 못 이긴 이격 상대를 더한다 |
| `sep_skip` | 이격 줄만 뺀다 (**지도에는 그린다**) |
| `road_side` | 도로라 이격 대상이 아닌 방향 |
| `win_pad` | 그림 창 여백 (그림에만 닿는다 — 값·판정과 무관) |

두 가지 규약이 있음.

**채운 사실은 값에 남음.** 적용 함수([[sitecheck/hand.py]])가 전부 `site.notes` 와 해당
Feature 속성에 「사람이 …했다」를 적음. 보고서는 `site.notes` 를 찍지 않지만 `demo.json` 에
남으므로, 종이의 숫자가 어디서 왔는지 값에서 되짚을 수 있음.

**`bld_id` 로 가리키는 것은 PNU 를 함께 적음.** `N####` 는 창 안 기하 순으로 매기는 번호라
(8절) GT 나 창이 바뀌면 같은 번호가 다른 건물을 가리킬 수 있음. PNU 가 어긋나면 조용히
엉뚱한 건물에 손대지 않고 **건너뛰며 그 사실을 찍음.**

### 산출물 5건 — 무엇이 코드에서 나오고 무엇이 손판인가

`hand_writting.py` 를 돌리면 값·레이어·그림·HTML 이 전부 다시 나옴. **보고서 PDF 만
예외다** — 저장소에 든 것은 Chrome 으로 인쇄한 손판이라(`/Producer Skia/PDF`) matplotlib 으로
다시 뽑으면 판이 무너짐. 그래서 PDF 는 **안의 글자·표·그림만 갈아 끼운다**
([[sitecheck/report/refit.py]] · [[sitecheck/report/pdf_refit.py]]).

실측(2026-08-24, 리팩터 전후 대조):

    demo/      65개 파일 중 코드가 그대로 재현 62 · 손판 PDF 3
    demo_cmp/  72개 파일 중 코드가 그대로 재현 70 · 손판 PDF 2

### 범례 — 종이를 **화면에** 맞춤

범례의 색칸은 **그림을 그린 팔레트에서 그대로 나온다**([[sitecheck/draw.py]]). 그런데 손으로
만든 PDF 의 범례는 그 팔레트가 바뀌기 전에 찍힌 것이라 그림과 갈릴 수 있다 — 실측 2026-08-25:

| 어디 | 종이가 말한 것 | 그림이 그린 것 |
|---|---|---|
| 고잔동 3면 | 「목재·팔레트」 + 「그 밖의 적치물」 **두 색** | **한 색**(적재 구역) |
| 비교 신당동 3면 | 「그 밖의 적치물」 | 「적재 구역」 |
| 호림동 2면 | 위험 · 안전 **둘** | 위험 · **주의** · 안전 셋(주황 측정선이 있는데 범례에 없었다) |

적재물의 **종류별 색은 2026-08-23 에 걷어 냈다**(종류는 겉모습으로 가른 값이라 지도에 색으로
박으면 확정한 것처럼 읽힌다 — 종류는 표에서 읽는다). 종이만 그 전 판으로 남아 있었음.

`hand_writting.py` 는 종이를 고치기 **직전에** HTML 을 새로 내므로, 범례는 그 HTML 에서 읽어
그대로 옮긴다([[sitecheck/report/refit.py]] `fix_legends`) — 값에서 다시 뽑으면 「어느 함수가
정답인가」가 한 벌 더 생기고 그 두 벌이 갈리는 순간 종이가 또 어긋남. 자리·칸 크기·글자
크기는 **원본에서 재서** 그대로 쓰고, 이름이 이미 같으면 손대지 않음.

`--verify` 는 고친 PDF 를 **다시 읽어** 우리 값과 대조한다 — 고치는 코드와 다른 길로 재므로
「고쳤다고 했는데 안 고쳐진」 상태를 잡음. 표(줄 수·글자)와 **그림이 제 면에 실렸는지**를
셋 다 봄.

> **그림 자리 검사를 더한 까닭.** 표만 대조하던 동안 호림동 3-10 보고서는 **3면(야외 적재물)
> 자리에 미등록증축 그림**을 실은 채로 저장소에 들어 있었다(2026-08-24 발견). 갈아 끼울 그림을
> 고를 때 쪽의 **자원 목록**을 셌는데, 거기에는 예전 갈아 끼우기가 남긴 그려지지도 않는 항목이
> 섞여 있어서 세 번째 이름이 3면의 같은 자리에 두 번 들어갔음. 이제 **실제로 그려지는 것만**
> 센다(`get_image_info`) — 덤으로 갈아 끼울 때마다 파일이 붓던 것도 멎었다(호림동 18.8 →
> 23.3 MB 로 커지던 것이 18.8 MB 그대로).

## 7. 좌표 프레임 — 받은 것을 그대로 지도에 얹으면 맞음

내보내는 모든 좌표는 **EPSG:4326 지도 좌표**다. `frame: {"name": "map"}` 이 그것을 말함.
받는 쪽은 보정값을 조합하지 않는다 — geojson 네 장만 있으면 그림.

**예전에는 그렇지 않았음.** 위성 정사영상은 절대측위 편이가 있어서 지도와 어긋나는데,
그때는 영상을 기준으로 두고 들어오는 지도 기하(연속지적도 필지 · GIS건물통합정보 footprint)를
전부 영상 쪽으로 끌어왔음. 값끼리는 맞았지만 좌표가 지도 좌표가 아니어서, 지도에 얹으면
장면마다 어긋났다(실측 구미 2~5 m · 대구 4~5 m · 남동공단 9 m). 받는 쪽이 `vector_shift_px` ·
`vector_shift_extra_m` · `parcel_bias_m` 을 직접 합쳐 되돌려야 했고, 픽셀과 미터가 섞여
있었음.

지금은 뒤집었다 — **영상의 지오레퍼런스를 되돌리고 지도 기하는 아무도 옮기지 않음.**
어느 쪽이 틀렸는지는 처음부터 정해져 있었다: 필지와 footprint 는 서로 다른 출처인데 같은
방향으로 같이 어긋나므로, 함께 틀릴 수는 없고 어긋난 쪽은 영상임.

    보정 전   지도 기하 += S        (영상 프레임으로)   → geojson 이 지도와 어긋남
    보정 후   지오트랜스폼 원점 -= S (지도 프레임으로)   → 그대로 얹으면 맞음

재는 방법은 그대로다(`parcel_fit` 엣지 정합 → `align` 모델 정합). 그 값을 지도에 더하는
대신 영상에서 뺌. 픽셀↔경위도 변환은 전부 `steps/georef.py` 를 지나므로 프레임이 갈릴
곳이 없음.

**검증**(데모 18주소 · 건물 폴리곤을 GIS건물통합정보와 IoU 로 짝지어 중심 편차):

    옛 프레임   구미 2~5 m · 대구 4~5 m · 남동공단 9.2~9.3 m
    새 프레임   0.0~1.6 m  (짝 3동 이상인 주소는 0.0~0.7 m)

### 여전히 지도 쪽에서 움직이는 것 — 필지 하나

연속지적도 필지 레이어는 대구에서 영상과 footprint **둘 다**에 대해 24 m 남쪽에 있음
(지적불부합). 영상을 고쳐도 그 24 m 는 남음. 필지가 그만큼 밀리면 야적 영역(필지−건물)과
대지경계선 이격이 남의 땅에서 나오므로 옮기고(`parcel_bias.py`), 옮긴 양을
`frame.parcel_shift_m` 에 적음. 그러므로 **대구에서는 우리 필지가 고객 지도의 지적도
레이어와 그만큼 어긋나 보인다** — 그 지적도 자신이 항공사진과 어긋나 있기 때문임.
구미·남동공단은 0 임.

### 영상을 함께 띄우려면

geojson 은 지도 좌표인데 원본 tif 는 아직 밀려 있음. 우리 영상을 배경으로 깔면 결과가
**우리 영상과** 어긋난다(고객 배경지도와는 맞고). 그때 쓸 보정 지오트랜스폼을 장면맘
파일로 남김.

```bash
python -m sitecheck.steps.georef --write     # assets/scenes/<장면>/georef.json
```

`transform_fixed` 와 그것을 넣는 `gdal_edit` 명령이 그 안에 있음. 단, 이 값은 **장면 평균**
이다 — 판정에는 주소마다 국소로 잰 값이 쓰이므로(정사보정 오차가 장면 안에서 위치를 탄다)
몇 m 다를 수 있음.

### 옛 결과를 섞지 않음

`schema_version` 1.0 결과는 영상 프레임임. 새 것과 한 화면에 섞으면 변화가 아닌 것이
변화로 보이므로, 비교분석(`report/compare`)과 레이어 물려받기(`pipeline.inherit`)는 옛 결과를
재사용하지 않고 다시 만듦. 저장된 `site` 를 다시 쓰는 곳(`analyze.load_site`)은
`georef.migrate` 로 프레임을 옮긴다 — V-World·건축물대장 조회 결과를 버리지 않으려고
다시 해석하지 않음.


## 8. 건물 번호 — 미리 정해 두는 것

이격 결과는 `pair: ["B0001", "N0011"]` 처럼 **두 건물을 가리킴.** 그러므로 번호는 판정봄
먼저 정해져 있어야 하고, 가리킨 것이 결과 안에 있어야 함. 예전에는 둘 다 아니었다 —
옆 지번 건물은 저장하지 않아서 `pair[1]` 이 어디에도 없는 id 를 가리켰고, 보고서는 그 id 를
되찾으려고 **추론을 다시 돌린 뒤** 중심점으로 걸러 냈음.

### 누가 매기나

`steps/s1_building.label_features` **한 곳**임. 모델 경로(`run.py`)와 GT 경로
(`demo.py`·`hand_writting.py`)가 같은 함수를 부른다 — 예전에는 각자 매겨서, 같은 건물이 도구에 따라
다른 번호를 받을 수 있었음.

### 규칙

| | 형식 | 순서 |
|---|---|---|
| 이 지번 건물 | `B0001` `B0002` … | **북→남, 같은 줄이면 서→동** (폴리곤 중심) |
| 옆 지번 건물 | `N0001` `N0002` … | 같음 |
| 야적 구역 | `Y0001` `Y0002` … | 같음 (`steps/s2_yard`) — 표에 싣는 **순서**는 판정 순이지만 번호는 기하 순이다 |

### 번호가 둘이다 — **줄의 번호**와 **상대의 번호**

이격 표에는 번호 칸이 둘이고, 재는 것과 상대가 다른 것이라 그렇음.

| 칸 | 무엇의 이름인가 | 지도 어디 | 정하는 곳 |
|---|---|---|---|
| **이격 번호** | 그 **측정선 하나** — 1 · 2 · 3 … | 거리 배지(「1 · 2.8 m」) | `draw.sep_ids` |
| **외부건물 번호** | 그 줄이 가리키는 **상대 건물** — ① · ② · ③ | 회색 배지(「①외부」) | `draw.ext_names` |

한 상대를 우리 동 둘이 마주 서거나 한 상대가 떨어진 두 구간을 이기면 **줄은 둘인데 상대는
하나**다. 한 칸에 두 뜻을 담으면 그때 반드시 한쪽이 거짓이 되므로(그래서 한때 지도에
「⑤⑥외부」가 나왔다) 이름을 둘로 가름.

    이격 번호   표에 나오는 차례로 **오름차순** — 동 이름 순(A동 → B동), 그 표 안에서는
                필지 밖(둘레 자리 순) → 대지경계선 → 필지 안(상대 동 이름 순)
    같은 값     **필지 안 쌍은 두 표에 한 줄씩 서지만 번호는 하나**다(A동 표의 6 = B동 표의 6)
                — 잰 선이 하나이기 때문임. 뒤 표에서만 번호가 거꾸로 보이는데, 그것이
                「이 줄은 앞 표에서 이미 센 그 선」이라는 뜻임
    비교분석    이 번호는 **두 날짜 사이에 짝지어지지 않는다**(이웃이 하나 늘면 뒤가 밀린다)
                — 그래서 변화 표에는 외부건물 번호만 싣음

### 지도·표의 ①②③ — **외부 건물마다 하나**

`B0001`·`N0011` 은 **건물의 id**(값 파일 안의 일련번호)이고, 종이와 지도에 보이는 ①②③ 은
사람이 부르는 **그 건물의 이름**이다(`draw.ext_names`) — 이 지번 건물에 「A동」을 주는 것과
같은 층윔. **한 건물에 이름은 하남.**

    자리    지도의 「⑤외부」 배지 · 표의 「외부건물 번호」 칸 — 둘이 같은 **건물**을 가리킴
    순서    **둘레 위 자리**(부지 북쪽부터 시계방향, `arc_m`). 자리가 같으면 **방위각**으로
            가른다 — 손으로 더한 줄은 `arc_m` 이 「그 상대에게 가장 가까운 경계선 위 자리」라
            모서리를 낀 상대 셋이 같은 값을 가질 수 있다(호산동 702-5)
    자격    이격 표에 실리고 **창 안으로 배지 하나 높이(4 m)만큼 들어온** 상대만
            (`draw.label_box`). 창에 스치기만 해도 번호를 주면 지도에 없는 것을 가리키는
            번호가 생긴다 — 호산동 702-5 의 남동 상대는 지붕의 0.7 % 만 모서리에 걸쳐
            있는데 ⑤ 를 가져갔고, 그 배지는 세 픽셀짜리 조각 위에 얹혀 있었음
    번호 없는 줄  **재지 않은 것으로 하고 종이에서 뺀다**(사용자 결정, 2026-08-27,
            `draw.sep_hidden`) — 번호가 없으면 지도에서 되짚을 수 없는 값이기 때문임.
            표·지도·1면 집계가 같은 함수로 같은 줄을 뺌. **값 파일(`separation.geojson`)
            에는 그대로 남음.** 단 **위험·주의인 줄은 번호가 없어도 빼지 않는다** — 그건
            창이 잘못 잡혔다는 신호이고, 지우면 위험이 조용히 사라진다(번호 없이 방위와
            거리로 싣는다: 「남동 4.2 m」). 실측 21곳 필지 밖 164줄 중 번호 없는 줄은
            3줄이고 셋 다 「안전」이었다(여백 26 m 일 때 잰 값) — 번호를 못 받으려면
            창(필지 bbox + `draw.WIN_PAD_M`) 가장자리에 걸쳐 있어야 하는데, 위험·주의는
            10 m 미만이라 늘 창 한복판임. **여백을 20 m 로 줄인 뒤**(2026-08-27) 저장된
            5물건에 다시 재 보니 그런 줄은 두 줄 늘었고(호산동 702-5 의 21.3 m · 29.8 m)
            둘 다 「안전」이라 판정은 그대롬

**한 건물이 두 표에 나올 수 있음.** 우리 동이 둘이면 같은 이웃까지의 거리를 A동에서도 B동에서도
재기 때문임. 그때 **번호는 같고 줄이 둘**이다 — 「A동 표의 ⑤ 17.3 m」와 「B동 표의 ⑤ 17.5 m」
는 **같은 건물을 두 동에서 잰 값**이라는 뜻이고, 표가 동마다 갈려 있어(`sep_dong_rows`) 어느
동에서 잰 값인지 헷갈리지 않음. 줄을 버리지는 않는다 — 하나를 지우면 그 동의 위험이 종이에서
사라짐. 지도에도 「⑤ 17.3 m」과 「⑤ 17.5 m」 두 배지가 서고, 측정선의 반대쪽 끝이 어느 동에서
잰 것인지 말함.

한때 번호를 **줄마다** 매겼다(2026-08-26). 그러면 한 건물이 번호를 둘 가져 지도의 이름 배지가
「⑤⑥외부」가 되는데, ①②③ 은 건물의 이름이라 한 건물이 두 이름을 가질 수 없다 — 지도만 보면
거기 건물이 둘 있는 것처럼 읽힌다(실측 호림동 3-10 남쪽 · 고잔동 672-6).

**기하로만 매김.** 폴리곤이 나온 순서로 매기면 모델 출력이 조금 달라질 때 번호가 전부
밀려, 같은 물건을 두 번 돌려도 다른 id 가 됨. 접두어를 나눈 이유는 `pair` 를 볼 때
**두 번째가 남의 땅 건물인지 한눈에 알아야** 하기 때문임.

### 이름표는 **자기 도형 위에** — 자리 잡는 법

「A동」이 옆 지번 건물 위에 있으면 **그 건물이 A동**이고, 「⑤외부」가 창 구석에 있으면 ⑤ 가
어느 건물인지 지도에서 되짚을 수 없음. 이름표의 자리는 꾸밈이 아니라 **판정의 일부**다.

예전에는 자리를 도형 **bbox 의 왼쪽 위 모서리 위쪽**으로 잡았음. 그 점은 도형 안이라는 보장이
없다 — 저장소의 결과 21곳 185개 이름표를 다시 재 보면 **자기 도형 안에 떨어진 것이 8 %**
(14/185)뿐이었고, **다섯 중 하나(20 %)는 아예 캔버스 밖**이라 창 안으로 당겨지면서 구석으로
날아갔다(앵커에서 창 안 도형까지 최대 1,000 px). 겹치면 **세로로만** 밀었으므로 배지가 한 줄로
쌓여 둘 다 남의 건물 위에 섰음.

지금은 세 단계다(`draw.px_poly` · `label_anchor` · `spot_on`). 셋 다 **창으로 자른 도형**
위에서 한다 — 창 밖은 놓을 자리가 아님.

    ① 앵커    도형 안에서 **경계에서 가장 먼 점**(pole of inaccessibility). 오목하든
              기울었든 늘 도형 안이고, 창으로 자른 뒤에 잡으므로 늘 창 안임
    ② 후보    앵커에 얹은 자리부터 **열두 방향**으로 배지 높이의 배수만큼(최대 3.4배) 나가 봄
    ③ 점수    **남의 도형을 덮으면 큰 벌점**(그 건물의 이름표로 읽힌다) · 자기 도형에서
              벗어나면 작은 벌점 · 앵커에서 멀면 거리만큼. 가장 싼 자리에 놓고, 그래도
              멀어졌으면 **지시선**을 긋음. 자리를 못 얻으면 **놓지 않는다**

같은 21곳을 이 규칙으로 다시 그리면 **299개 이름표가 전부 자기 도형 위에** 앉고(덮은 넓이
중앙값 100 %), 290개는 앵커에서 한 픽셀도 움직이지 않으며, 자리를 못 얻어 빠진 것은 없음.

네 그림이 **같은 함수**를 쓴다 — 이격의 「A동」·「①외부」, 야적의 「A동」·「Y0001」, 대장의
「A동 일치」, 폴리곤 판의 「A동 · 1,234㎡」가 모두 그렇음.

### 사람이 읽는 이름

| 대상 | 값 | 정하는 규칙 |
|---|---|---|
| 이 지번 건물 | `dong` = `"A동"` | **건축면적 큰 순** (화면설계서 BR-13 목업) · 면적이 같으면 `bld_id` 순 |
| 옆 지번 건물 | `az_deg` · `dist_m` | 번호(①②③)를 **값에 박지 않는다** — 아래 |

①②③ 은 **북쪽부터 시계방향**으로 붙지만 어느 건물에 붙일지는 그림마다 다르다(창 밖이거나
창에 얕게만 걸치면 배지를 놓을 자리가 없고, 이격 표에 없는 건물은 번호를 받지 않는다). 그래서 번호 대신
**순서의 근거**를 담는다 — `az_deg`(필지 중심에서 본 방위, 북 0° 시계방향)와
`dist_m`(가장 가까운 대상 건물까지 거리). 보여 줄 건물을 `az_deg` 로 정렬해 ①부터 붙이면
우리 그림과 같은 순서가 됨.

### 이격 `pair` 읽는 법

- `pair[0]` 은 **항상 이 지번 건물**이다(그 건물의 행이라는 뜻).
- 대상 건물끼리의 쌍은 **양쪽에서 한 번씩, 두 줄로** 나온다(`B0001→B0002` 와 `B0002→B0001`).
  건물마다 「내 둘레에 무엇이 있나」를 다 적는 표라 그렇다 — 쌍의 개수를 세려면 절반임.
- `kind: "lot_line"` 인 줄은 상대 건물이 아니라 **대지경계선**까지의 거리이고 `bld_id` 하나만 있음.

### 판정이 가리키는 것

| 레이어 | 가리키는 key | 대상 |
|---|---|---|
| `separation` | `pair` `[0]`·`[1]` · `bld_id` | 건물 (`B…` 또는 `N…`) |
| `ledger` | `bld_id` | 이 지번 건물 |
| `yard` | `near_bld_id` | 거리를 잰 그 건물 |

`schema.validate` 가 **가리킨 id 가 결과 안에 있는지** 본다(`known_ids`). 없으면 저장할 때
`[!!] 형식 점검` 으로 찍힌다 — 조용히 나가지 않음. `pipeline.finish` 가 매번 부름.

### 건물이 어느 지번인가 — `owner` 는 PNU 다

건물 feature 의 `owner` 는 **19자리 PNU 이거나 `null`** 이고, `site.pnu` · `site.neighbors[].pnu`
로 풀린다(그 지번의 건축물대장·층수가 거기 있다). 1.2 까지는 필지 지분으로 정한 경우
`par:3` 처럼 나갔는데, 그 3 은 `[이 필지] + 인접필지` **메모리 목록의 색인**이라 받는 쪽이 풀
수 없었다 — 실측으로 이웃 581동 중 127동, 대상 60동 중 40동이 그 형태였음. `validate` 가
이제 PNU 모양(19자리 숫자)인지 봄.

어떻게 정했는지는 `owner_by` 가 말함.

| `owner_by` | 뜻 |
|---|---|
| `footprint` | GIS건물통합정보 footprint 와 25 % 이상 겹쳤다 — **그 자산이 지번을 직접 말해 준다** |
| `parcel` | footprint 가 없다(= 미등록 건물). 필지와 겹친 지분이 가장 큰 지번으로 정했다 |
| `null` | 어느 필지에도 25 % 이상 걸치지 않았다 |

### 모양이 바뀌면 판 번호를 올림

저장된 결과를 **다시 써도 되는지**는 `schema.is_current`(판 번호 + 프레임)가 정한다 —
비교분석(`report/compare`)의 날짜별 결과 재사용과 레이어 물려받기(`pipeline.inherit`)가 그것을
봄. 프레임만 보던 동안 실제로 사고가 났다: id 규약을 바꿨는데 판 번호를 안 올려서,
비교분석이 **옛 id 로 만든 t1·t2 를 재사용**했고 옛 `pair` 와 새로 되찾은 `N####` 이 섞였음
(①②③ 이 엉뚱한 건물에 붙는다). 그래서 출력 모양을 건드리면 `SCHEMA_VERSION` 을 올리고
저장된 산출물을 다시 만듦.

    1.0   옛 영상 프레임 (지도에 얹으면 어긋난다)
    1.1   지도 프레임 (7절)
    1.2   건물 id 규약 · `context` · `level_rank` (이 절)
    1.3   `owner` 가 PNU 로만 · `owner_by` · `floors_src`

### 지번을 말할 수 없는 이웃 건물

`owner: null` 인 건물이 나올 수 있다 — 아는 필지 어디에도 25 % 이상 걸치지 않은 경움.
실측(데모 40개 결과): `pair` 가 가리킨 이웃 **346건 중 2건**이 그렇고, 층수를 못 정한 자리는
**1,408건 중 29건**임. 원인은 인접필지 조회 반경(`NEIGHBOR_PAD_DEG` ≈ 130~165 m)이
건물 탐지 창(필지 bbox ±80 m)보다 좁을 수 있어서다 — 실측 호산동 357-70 의 `N0026` 은
9,475 ㎡ 공장인데 아는 필지와 0.4 % 만 겹침.

**지어내지 않음.** 그때 `owner` 는 `null`, 층수는 `null`, `floors_src` 는 `empty` 로 나가고
판정은 보수적으로 2층 기준(10 m)을 씀. 반경을 넓히면 줄어들지만 주소마다 V-World·대장
조회가 늘어나므로 그대로 두었음.

### 야적 거리는 아직 이 지번 건물까지만 잼

`yard` 의 `dist_to_building_m` 은 **이 지번 건물**까지의 최단거림. 옆 지번 건물이 더
가까워도 잡히지 않는다(실측 구미 공단동 282: 1·2번 구역이 이 지번 건물까지 150·163 m 인데
옆 지번 건물까지는 31·30 m). 이격(A1)은 「연소는 지번 경계를 넘어 옮겨붙는다」며 옆 필지
건물까지 재므로 규칙이 엇갈린다 — 바꾸면 A5 등급이 달라지므로 판단을 남겨 두었음.
